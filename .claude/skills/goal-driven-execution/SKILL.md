# Goal-Driven Execution

LLMは曖昧な命令には弱いが、**検証可能なゴールに向かってループする**のは得意。タスク開始時に「成功基準」を先に固めることで、作業中の迷走と人間への打ち返しを最小化する。

## いつ使うか

- 複数ステップ・複数日にまたがる施策やタスクの着手前
- 指示が曖昧（「進めて」「いい感じに」「なんとかして」）なとき
- 「終わったかどうか」が後から揉めそうなとき

使わない場面:
- 1アクションで終わる自明なタスク
- 調査・質問応答など成果物の検証が不要なもの

## 核となる変換

命令形を**検証可能なゴール（受け入れ基準）**に置き換える:

| Instead of... | Transform to... |
|--------------|-----------------|
| "資料を良くして" | "レビュアーAが指摘した3点が全て反映されている" |
| "顧客対応して" | "顧客から返信が来て、次アクションが確定している" |
| "段取りして" | "担当・期限つきのタスクリストが合意済みになっている" |
| "改善して" | "指標Xが現状YからZへ動いたことを数値で示せる" |

## ワークフロー

1. **AC（受け入れ基準）を箇条書きで定義**
   - 各ACは**客観的に検証可能**な形に落とす（誰が見ても達成/未達が判定できる）
   - 検証不可なAC（「体験を良くする」等）は受け入れず、観測可能な形に再定義する

2. **マルチステップなら検証付き計画を提示**
   ```
   1. [ステップ] → verify: [何を見れば完了と分かるか]
   2. [ステップ] → verify: [check]
   3. [ステップ] → verify: [check]
   ```

3. **AC合意後に実行**
   - 合意 → 実行 → 各ステップで verify → 完了報告
   - AC範囲外の新規事項は勝手に拡張せず、`workspace/inbox/` か該当プロジェクトノートの「タスク」へ送る（後出し封じ）

## アンチパターン

- **AC不在のまま着手**: 完了後に「これじゃない」となり手戻り
- **検証不可なAC**: 「分かりやすくする」「丁寧に対応する」→ 主観的で収束しない
- **過剰なAC定義**: 自明な単発タスクにまでAC、は逆に時間の無駄
